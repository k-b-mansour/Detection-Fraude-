# BC01 — Socle de données anti-fraude

## Résumé

Ce bloc pose les fondations data du projet : un entrepôt en étoile PostgreSQL organisé en
quatre couches (`staging` → `dwh` → `mart` → `ops`), un feature store en ligne Redis pour le
scoring temps réel, et un pipeline d'ingestion streaming Kafka. Batch et streaming empruntent
la **même fonction de transformation SQL** — le chemin ne peut pas diverger entre les deux
voies. L'ensemble est containerisé sous Docker et démarre en une seule commande.

Les données sont **entièrement synthétiques**, générées par `data/seed.py`. Ce choix est
délibéré : les datasets Kaggle de détection de fraude usuels (ex. *Credit Card Fraud Detection*,
ULB) réduisent les variables à des composantes PCA anonymisées (V1-V28), ce qui interdit un
schéma en étoile porteur de sens métier. Générer les données permet de contrôler le schéma, les
typologies de fraude et la volumétrie de bout en bout.

## Les quatre couches

| Couche | Rôle |
|---|---|
| `staging` | Copie brute des transactions, batch ou streaming, aucune règle métier |
| `dwh` | Schéma en étoile — dimensions + faits, alimenté par une seule fonction de transformation |
| `mart` | Vues de restitution — contrat d'interface pour BC02 → BC06 |
| `ops` | Journal des chargements + contrôles qualité, transversal, jamais sur le chemin critique |

## Pipeline d'architecture

```
   seed.py (batch)                          producer.py (stream)
        │                                          │
        ▼                                          ▼
  staging.raw_transactions  ◄──────────────  consumer.py
  (mode_ingestion='batch')                   (micro-lots de 200,
        │                                     JSON invalide → DLQ,
        │                                     dédup Redis, offsets
        │                                     committés après écriture)
        │                                          │
        └──────────────┬───────────────────────────┘
                        ▼
      dwh.charger_faits_transactions(mode)   ← fonction SQL UNIQUE
                        │
                        ▼
              dwh.fact_transactions
        (dim_clients, dim_temps, dim_canal, dim_agences)
                        │
                        ▼
                  mart.v_* (vues)
                        │
                        ▼
              BC02 → BC06 (consommateurs)

   ops.log_chargement / ops.controle_qualite : observent tout le flux
```

## Base de données — schéma en étoile (`dwh`)

| Table | Rôle |
|---|---|
| `dim_clients` | 5 000 clients pseudonymisés RGPD (aucun nom généré) — segment, revenu, agence gestionnaire |
| `dim_agences` | 10 agences du réseau — attribut du client, pas de la transaction |
| `dim_temps` | 1 ligne par heure sur l'année simulée + membre **Inconnu** (clé 0) |
| `dim_canal` | Combinaison canal de paiement / code MCC + membre **Inconnu** (clé 0) |
| `fact_transactions` | Grain = 1 transaction carte. `is_fraud`/`fraud_type` NULLables : une transaction stream entre dans le fait avant même d'être labellisée |
| `fact_card_blocks` | Historique des blocages carte — feature comportementale (BC02) |

### Le membre "Inconnu" (clé technique 0)

`dim_temps` et `dim_canal` portent chacune une ligne réservée, clé `0`, jamais générée par
`seed.py` ni par le flux Kafka. `dwh.charger_faits_transactions()` s'y replie (`COALESCE`) quand
une dimension ne matche pas — typiquement un événement streaming produit "aujourd'hui", hors de
la fenêtre simulée (année 2025). La transaction est écrite quand même : **aucune donnée n'est
perdue silencieusement**, la dégradation est visible (`temps_key = 0`) et traçable.

`client_id`, lui, reste en jointure **stricte** : un client inconnu est une vraie anomalie (le
producer ne pioche que des `client_id` réels), pas un cas à masquer. La ligne de staging
correspondante reste `traite = FALSE` et remonte via le contrôle qualité `staging_transforme`
si elle stagne plus de 10 minutes.

## `dwh.charger_faits_transactions()` — la porte unique

```sql
SELECT dwh.charger_faits_transactions('batch');   -- appelé par seed.py
SELECT dwh.charger_faits_transactions('stream');  -- appelé par consumer.py, par micro-lot
```

- Lit les lignes `staging.raw_transactions` non traitées (`traite = FALSE`) du mode demandé.
- Résout les dimensions (jointure stricte sur le client, tolérante sur le temps/canal).
- Insère dans `dwh.fact_transactions` avec `ON CONFLICT (transaction_bk) DO NOTHING`.
- Marque `traite = TRUE` uniquement les lignes effectivement résolues.
- Idempotente : rejouer un chargement déjà traité n'insère aucun doublon.

## Garanties d'idempotence

| Propriété | Mécanisme |
|---|---|
| Idempotence batch | `TRUNCATE ... RESTART IDENTITY` + clé métier déterministe `TX-000000001` |
| Idempotence stream | `ON CONFLICT (transaction_bk) DO NOTHING` + jeu de déduplication Redis (`dedup:{bk}`, TTL 24h) |
| At-least-once | commit de l'offset Kafka **après** écriture réussie en base — jamais avant |
| Pas de perte sur échec transitoire | le marquage Redis (dédup + features) n'a lieu qu'**après** succès Postgres — un lot en échec est rejoué tel quel |
| Zéro doublon producteur | `enable.idempotence = true`, `acks = all` |
| Messages malformés isolés | validation de schéma JSON avant insertion — rejet vers `transactions.dlq`, jamais de blocage du flux |

## Contrôles qualité (`ops.controle_qualite`)

`scripts/quality_checks.py` exécute 10 contrôles après chaque chargement et journalise le
résultat : complétude des FK, intégrité référentielle client, unicité de `transaction_bk`,
cohérence montant/distance/label, plausibilité du taux de fraude (0,5 % – 3 %), fraîcheur du
staging, conformité du référentiel agences/canaux.

```bash
python bc01_socle_donnees/scripts/quality_checks.py
# Résultat des contrôles qualité : 10/10 au vert
```

## Génération des données (`data/seed.py`) — voie batch

```bash
python bc01_socle_donnees/data/seed.py --clients 5000 --transactions 400000 --fraud-rate 0.015
```

Charge les dimensions, écrit les transactions dans `staging.raw_transactions` (déjà labellisées,
historique simulé), puis appelle `dwh.charger_faits_transactions('batch')`. Chaque exécution est
journalisée dans `ops.log_chargement`. Reproductible (graine aléatoire fixe).

## Simulation du streaming (Kafka)

```bash
python bc01_socle_donnees/streaming/consumer.py           # terminal 1 — ingestion continue
python bc01_socle_donnees/streaming/producer.py --rate 5  # terminal 2 — ~5 transactions/seconde
```

Le producer pioche des `client_id` réels dans `dwh.dim_clients`, génère `transaction_bk` une
seule fois (il voyage avec le message — une re-livraison Kafka ne change jamais la clé) et publie
sur `transactions.raw`. Le consumer traite par micro-lots de 200 messages (ou toutes les 2
secondes) : validation JSON → dédup Redis → écriture `staging` → transformation → mise à jour
du feature store en ligne (`feat:{client_id}:nb_tx_1h`, `feat:{client_id}:montant_cumul_1h`,
TTL 1h) → commit des offsets.

## Typologies de fraude simulées

| Type | Signature injectée dans les données |
|---|---|
| `usurpation_identite` | Authentification absente, distance domicile très élevée, pays à risque |
| `fraude_en_ligne` | Canal en ligne, montant élevé, transaction nocturne |
| `skimming` | Canal puce, transaction nocturne, montant modéré |
| `test_carte` | Canal en ligne, montant très faible (< 3€), sans authentification |
| `vol_carte_physique` | Canal sans-contact ou puce, distance domicile élevée, nocturne |
| `ingenierie_sociale` | Montant élevé, authentification 3DS présente (la victime valide elle-même) |

## Limites connues et pistes d'amélioration

- Le membre "Inconnu" de `dim_temps` sera systématiquement utilisé par toute démo streaming
  lancée hors de l'année simulée (2025) — comportement volontaire, mais qui masque la vraie
  fraîcheur temporelle des données de démonstration. Une version production régénérerait
  `dim_temps` glissant sur la période réelle.
- La fenêtre Redis des features (`INCR` + `EXPIRE`) est une fenêtre glissante approximative,
  pas une fenêtre exacte seconde par seconde (`ZADD`/`ZREMRANGEBYSCORE` en ferait une exacte).
- Kafka tourne en cluster à un seul broker (suffisant pour la démonstration).
- `dwh.charger_faits_transactions('batch')` prend environ 2 minutes pour 400 000 lignes — pas
  un problème pour cette échelle, mais une jointure moins naïve serait nécessaire au-delà.
