1. Objectif du bloc BC05

Un modèle qui vit dans un notebook ne protège aucun client. Le BC05 fait passer le LightGBM du BC03 du statut d'artefact évalué hors-ligne à celui de service interrogeable en temps réel : une API qui reçoit une transaction, la score en moins de 200 ms, explique sa décision, et tourne dans un conteneur reproductible plutôt que sur la machine de développement. Deux garde-fous accompagnent ce passage en production : un monitoring qui détecte quand les données réelles s'écartent de celles sur lesquelles le modèle a été entraîné, et un pipeline d'intégration continue qui empêche qu'une régression atteigne l'image livrée sans être testée au préalable.

2. Argumentaire méthodologique

L'API n'embarque pas l'ensemble de l'environnement du projet : une image de service n'a besoin ni de psycopg2, ni de confluent-kafka, ni de TensorFlow, ni de Matplotlib — seulement de ce qui sert une prédiction. requirements-api.txt isole ce sous-ensemble strict, ce qui réduit la taille de l'image et sa surface d'attaque, deux préoccupations réelles en production que requirements.txt (pensé pour l'entraînement et l'analyse) ne partage pas.

L'explicabilité SHAP, développée hors-ligne au BC03 pour analyser des lots de transactions, est ici recalculée à la volée pour chaque requête. Le coût est mesuré, pas supposé : un TreeExplainer initialisé une seule fois au démarrage du service évalue une ligne en quelques millisecondes, ce qui laisse une marge confortable sous la contrainte des 200 ms. C'est ce qui permet à l'API de répondre, pour chaque transaction, non seulement un score mais aussi « pourquoi » — la même obligation RGPD Art. 22 déjà posée au BC03, désormais tenue en production et non plus seulement démontrée sur un échantillon a posteriori.

Le feature store Redis construit au BC01 pour le streaming retrouve ici son usage prévu : si la requête porte un client_id connu, l'API interroge Redis pour joindre à la réponse les compteurs temps réel (nb_tx_1h, montant_cumul_1h) — à titre informatif, sans les injecter dans le modèle, qui n'a pas été entraîné avec ces variables. Redis étant une dépendance non critique de cette lecture d'appoint, sa perte ne doit jamais faire échouer une prédiction : l'API teste la connexion au démarrage et dégrade silencieusement (features_temps_reel: null) si elle échoue, plutôt que de renvoyer une erreur 500 pour un enrichissement secondaire.

Sur une transaction test (850 €, 320 km du domicile, 3 h du matin, en ligne, sans authentification), l'API renvoie un score de 1,000 et identifie distance_domicile_km comme facteur dominant (+11,51 en log-cote), suivi de heure (+4,56) — exactement la signature vol_carte_physique/usurpation_identite déjà caractérisée au BC01/BC03. À l'inverse, une transaction de 42,50 € en journée avec code PIN reçoit un score de 0,000. Ces deux cas, ainsi que le rejet propre d'une valeur de canal invalide (422, pas une erreur serveur) et l'enrichissement Redis vérifié de bout en bout (un client réellement actif dans le flux du BC01 renvoie ses compteurs temps réel dans la réponse), sont couverts par la suite de tests automatisés.

5. Conteneurisation — deux incidents réels, deux corrections

La construction de l'image n'a pas été immédiate, et les deux incidents rencontrés sont documentés ici plutôt que passés sous silence : ce sont exactement le genre de blocages qu'un environnement de conteneurisation réel produit, et leur résolution fait partie du livrable.

IncidentCauseCorrection
Échec SSL lors de pip install Le conteneur ne dispose pas du certificat racine du proxy réseau de cet environnement de développement --trusted-host sur les trois hôtes PyPI — sans incidence sur un réseau standard
libgomp.so.1: cannot open shared object file au démarrage LightGBM requiert le runtime OpenMP (libgomp1), absent de l'image python:3.10-slim apt-get install libgomp1 avant l'installation des dépendances Python

Le second incident illustre une limite générale des images « slim » : elles suppriment des bibliothèques système que Python ne réclame qu'indirectement, via les extensions compilées de ses dépendances. Le healthcheck Docker (HEALTHCHECK dans le Dockerfile, qui interroge /health toutes les 15 secondes) est justement ce qui aurait signalé ce défaut de démarrage en production avant qu'un système de routage n'envoie du trafic vers un conteneur mort.

6. Monitoring Evidently — détection de dérive

Deux scénarios sont comparés à la même référence (l'échantillon d'entraînement du BC03) : le test du BC03 tel quel, et une version où trois variables — heure, montant, mois — sont délibérément décalées pour simuler une évolution des habitudes de fraude. Le scénario normal détecte une dérive sur 9,1 % des colonnes (1 sur 11, sous le seuil d'alerte de 20 %) ; le scénario simulé en détecte 27,3 % (3 sur 11), déclenchant l'alerte.

Un résultat qui n'était pas entièrement prévu. La colonne mois apparaît en dérive dans le scénario normal également (score de Wasserstein le plus élevé des deux rapports), sans qu'aucun décalage n'y ait été simulé. La cause est le split temporel lui-même : le train du BC03 couvre dix mois de l'année quand le test n'en couvre que les deux ou trois derniers — leurs distributions de mois diffèrent donc réellement, par construction du découpage chronologique, pas par un changement de comportement des fraudeurs. C'est un rappel utile : un split temporel, nécessaire pour évaluer un modèle sans fuite d'information (BC03, section 2), produit par lui-même un déséquilibre calendaire qu'un monitoring de dérive détectera — sans qu'il s'agisse d'une anomalie à corriger.

7. CI/CD — pipeline et ce qui est réellement vérifié

Le pipeline (.github/workflows/ci-cd.yml) exécute deux jobs à chaque push ou pull request vers main : test installe les dépendances de service et lance la suite pytest ; build-image construit l'image Docker, la démarre, interroge /health jusqu'à quinze fois avant d'échouer, puis publie l'image sur GitHub Container Registry (ghcr.io) — uniquement sur un push vers main, jamais sur une pull request, pour qu'aucune image non relue ne devienne accessible. Poussé sur un dépôt GitHub réel, il s'est exécuté sur les runners GitHub Actions — pas seulement rejoué en local.

Le premier push a échoué : le job test plantait en 29 secondes (ModuleNotFoundError, code de sortie 2). Cause identifiée et reproduite en local à l'identique : le workflow invoquait pytest nu, qui n'ajoute pas la racine du dépôt à sys.path, contrairement à python -m pytest utilisé lors des vérifications manuelles. Une fois corrigé, test passait, mais la publication sur GHCR échouait à son tour, instantanément : un nom d'image Docker doit être en minuscules et ne peut ni commencer ni finir par un tiret — deux règles que le nom de ce dépôt (Detection-Fraude-) enfreignait une fois mis en minuscules. Le correctif final construit le nom de l'image à partir du seul propriétaire du dépôt plutôt que de son nom complet.

8. Synthèse et implications pour le BC06

Le BC05 clôt la chaîne technique du projet : un modèle entraîné et expliqué (BC03), comparé à des approches alternatives (BC04), est désormais servi par une API conteneurisée, mesurée sous la contrainte de latence réglementaire, et surveillée pour sa dérive. Trois éléments restent directement du ressort du BC06 : l'arbitrage entre les deux seuils exposés par l'API (0,5 et 0,98) relève d'une décision métier sur le coût comparé d'une fraude manquée et d'une fausse alerte, déjà posée mais non tranchée au BC03 ; la fréquence à laquelle drift_report.py devrait tourner en production, et la procédure de réentraînement qu'une alerte de dérive devrait déclencher, restent à formaliser ; et la conformité RGPD, déjà posée par l'explicabilité SHAP embarquée ici, mérite d'être complétée par un registre des décisions automatisées et leur durée de conservation.
